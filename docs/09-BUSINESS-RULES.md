# 09 — Business Rules

**Updated per `11-SCHEMA-DECISIONS.md` (approved)** — rework and re-audit rules added below (new sections); all other rules unchanged from the original design.

## Account Hierarchy

- Manager creates Team Lead. Manager creates Auditor.
- Team Lead creates Coder. A Coder is created under, and belongs to, the creating TL's team.
- Coder cannot create any user. Auditor cannot create any user.
- Team Lead cannot create another Team Lead. Team Lead cannot create an Auditor.
- All of the above are enforced server-side regardless of what the frontend allows the user to attempt.

## Chart / Production / Audit Relationship

- **Chart ID** is the single linking key between Production and Audit.
- A Chart can have **multiple Production versions** over time, but exactly one is ever "current" at a given moment. In normal (non-rework) operation, a Coder creates exactly one version and that remains current permanently.
- An Auditor never manually re-enters production information. The Auditor enters only a Chart ID; the system retrieves the **current** linked Production version.
- A Production version can have **multiple Audit records** over time, but normal operation produces exactly one. A second audit against the same version is only possible as an explicit re-audit (see below), which requires the first audit to be `REJECTED`.

## Production Rework

- A `COMPLETED` Production record cannot be edited directly by anyone, including the Coder who created it.
- To correct it, the Coder (or a TL directing the correction) sets it to `REWORK`. This creates a **new Production version**, pre-filled from the current version's data, editable by the Coder. The original version is preserved unchanged and remains queryable in history.
- Once the Coder resubmits (`IN_PROGRESS → COMPLETED` on the new version), the new version becomes current; the previous version's `isCurrent` flag is cleared but the row is never deleted.
- A TL or Manager may `CANCEL` a Production record (e.g., miscoded/wrong project) at any point before it is audited; cancellation is a status change, not a deletion.
- Every status transition on a Production record — creation, rework initiation, cancellation — is written to the compliance `AuditLog`, in addition to the domain data itself preserving the version history.

## Audit Resolution & Re-audit

- A `COMPLETED` Audit Entry cannot be edited by anyone. Corrections happen only through the re-audit path below, never by mutating a finished audit.
- If an Auditor flags an audit `REVIEW_REQUIRED`, only a TL (for their own team's charts) or a Manager can resolve it — to either `COMPLETED` or `REJECTED`.
- `REJECTED` on an audit means the underlying production needs correction; it is the trigger a Coder sees to initiate rework (Production Rework, above).
- Re-auditing the same Production version (as opposed to a fresh audit following a rework-produced new version) is only permitted when the existing audit's status is `REJECTED`. Re-audit **always creates a new `AuditEntry` row** — the original is never overwritten — so historical accuracy/CPH metrics and Auditor performance tracking remain correct as of the time they were recorded.

## Identity Rules

- Coder identity (Name, Employee ID, Login Name) is always derived from the authenticated session — never a manually typed field on the Production form.
- Auditor identity (Name, Employee ID, Login Name) is always derived from the authenticated session — never a manually typed field on the Audit form.

## Production Fields

Required: Chart ID, Page Count, Total ICDs, Total DOS, Status, Coded Date.
Optional: Remarks.
**No JCD field exists on this form, in this table, or in any calculation derived from it.**

## Audit Fields

Auto-retrieved (read-only to the Auditor): Coder Name, Coder Employee ID, Coder Login Name, Page Count, Total DOS, Total ICDs, Coded Date, Production Status.

Entered by Auditor: Audit Errors, Error Exceptions, Status, Audit Date, Remarks.

System-calculated: **Total Number of Errors = Audit Errors + Error Exceptions.** This calculation happens in the backend and is authoritative; the frontend may echo it for display but the persisted value always comes from a server-side recomputation at write time.

**No JCD field exists on this form, in this table, or in any calculation derived from it.**

## Chart Assignment

- AUTOMATIC-allocation-type projects (the default - see "Client File Driven Chart Import" below) keep v1's original behaviour unchanged: a Coder enters a Chart ID directly on the Production form, and the system creates the Chart record automatically if it doesn't already exist.
- The schema reserves `assignedCoderId`/`assignedById`/`assignedAt` on Chart for a future formal Manager→TeamLead→Coder allocation workflow (Phase 10D), but business logic still does not populate or enforce these fields as of Phase 10A-10B.
- Visibility: Manager sees all charts. A Team Lead sees charts belonging to projects assigned to their team. A Coder sees charts they have personally submitted production against.

## Auditor Assignment

- A Manager assigns each Auditor to one or more Projects (`AuditorProjectAssignment`).
- An Auditor's queue is every chart within their assigned project(s) whose current Production status is `COMPLETED` and which has no open (`PENDING`/`IN_PROGRESS`) audit — the Auditor is not restricted to individually pre-assigned charts within that project.
- An Auditor cannot fetch or audit a chart outside their assigned projects.

## Productivity / CPH

Charts Per Hour is derived from configurable inputs (charts, hours, pages, DOS, ICDs) via a formula that is not hardcoded into application logic — it reads from a configuration record so the business can adjust the CPH definition without a code deployment. No additional medical-coding metrics (e.g., no JCD-based metric) are introduced beyond what's explicitly listed here.

## Reporting

Production and Audit reports expose exactly the field sets specified in the brief (Chart ID, Coder, Employee ID, Pages, DOS, ICDs, Status, Coded Date for Production; the equivalent Audit field set including Total Errors) — no additional invented columns, and specifically no JCD column.

## Login Name Allocation & History (Phase 9)

- Login Name is an auditable **allocation identity**, not merely a mutable field on `User`. Every Login Name ever held by every account (Internal/Vendor/TL/Coder/Auditor) is recorded, append-only, in `LoginNameAllocation`.
- **Invariant, enforced in the database** (PostgreSQL partial unique indexes, not just application code): at most one `ACTIVE` allocation may exist for a given `loginName`, and at most one `ACTIVE` allocation may exist for a given `userId`.
- Status is one of exactly `ACTIVE`, `DEACTIVATED`, `REALLOCATED` — no other statuses exist.
- History rows are **never overwritten or deleted**. Reassigning a Login Name closes the existing `ACTIVE` row (`status → REALLOCATED`, `deallocatedAt`/`deallocatedById` set) and creates a new `ACTIVE` row, both inside one database transaction.
- The existing Login Name change workflow is unchanged and still authoritative: a Team Lead requests a Coder's Login Name change → Manager approval → `UsersService.changeLoginName` applies it. That same call now also reassigns the `LoginNameAllocation` history, in the same transaction as the `User.loginName` update, the `ApprovalRequest` completion, and the audit log entry — if any step fails, the entire change (including the Login Name itself) rolls back, so a Login Name is never changed without its allocation history changing to match, or vice versa.
- A Manager may search and view current/historical allocations, but cannot reassign a Login Name from the allocation screens directly — reassignment only happens through the approved change workflow above.
- Historical allocation rows join to the user's **current** organizational placement (vendor/team/team lead) for display — they are not a point-in-time snapshot of the org structure at the time of allocation.
- Pre-existing accounts (from before Phase 9) are backfilled by a standalone, idempotent script (`apps/api/scripts/backfill-login-name-allocations.ts`), not by the migration itself — this avoids depending on a database-generated UUID function that isn't used anywhere else in this schema. The script is safe to re-run: it skips any user who already has an `ACTIVE` allocation.
- Backfilled rows leave `allocatedById` **null** rather than attributing the allocation to the account holder themselves or to a fabricated Manager — there is no real historical actor to record for a pre-existing account. This mirrors `AuditLog.userId`, already nullable in this schema for system-origin events. `allocatedById` is nullable for exactly this reason; every allocation a real Manager creates or reallocates always carries a real `allocatedById`. Backfilled rows are explicitly marked via `reason = 'INITIAL_BACKFILL: ...'` and are also logged to `AuditLog` (`action: 'LOGIN_NAME_ALLOCATION_BACKFILLED'`, `userId: null`).
- Every allocation/reallocation is written to the existing `AuditLog` — there is no separate/parallel audit mechanism for Login Name history.

## Manager Login Name Details (Phase 9)

- Manager-only screen (`/manager/login-name-details`) for searching Login Names by Login Name, Employee ID, Employee Name, or Email, with Role/Vendor/Team/Team Lead/Status filters.
- Selecting a result shows its current allocation plus its complete history — reachable, but not editable, from this screen.

## Employee Directory (Phase 9)

- Manager-only screen (`/manager/employees`) — a searchable, paginated, enterprise-wide account directory. It is not a CRM/ATS.
- Columns: EMP-ID, Employee Name, Login Name, Email, Role, Vendor, Team, Team Lead, Active/Inactive, Created Date. There is intentionally no Online/Offline column — no presence/session tracking exists yet in this system, and this phase does not invent placeholder presence data.
- Search and every filter (Role, Active/Inactive, Vendor, Team, Team Lead) are server-side; the directory is always paginated and the full list is never loaded into the browser at once.
- The detail view groups fields as Identity (EMP-ID/Name/Email/Login Name), Account (Role/Active-Inactive/Created Date), and Organization (Vendor/Team/Team Lead), plus the employee's Login Name allocation history. Password hashes, reset tokens, and access/refresh tokens are never returned by the API and never rendered.

## Project Allocation Type (Phase 10A)

- Every Project has an `allocationType`: `MANUAL` or `AUTOMATIC`. **`AUTOMATIC` is the default** for every existing and newly-created project. This is a **factual backfill, sourced below - not a guess or a silent classification**: `MANUAL` (client-file-driven allocation) did not exist as a concept before this migration, so `AUTOMATIC` is the only value that can be historically true of any pre-Phase-10 project.
  - **Source proving the mapping:** `apps/api/src/modules/production/production.service.ts`'s `if (!chart) await tx.chart.create(...)` call is, as of this migration, the **only** Chart-creation code path that ever existed prior to this phase's own new `ChartImportsService.commit` (a repo-wide search for `chart.create`/`chart.createMany`/`chart.upsert` finds exactly these two call sites, nowhere else). That path never branched on any project-level flag - none existed - so every Chart on every existing Project was necessarily created by it, proving `AUTOMATIC` is the only value any pre-Phase-10 Project could ever have been.
  - Backfilled explicitly by the migration itself (`ALTER TABLE "Project" ADD COLUMN "allocationType" ... NOT NULL DEFAULT 'AUTOMATIC'`, which Postgres applies to every existing row as part of that same statement), so no current project's behaviour changes as a side effect of this migration.
- `MANUAL` means the project's Charts come from a Manager-imported client file (see "Client File Driven Chart Import" below) rather than from a Coder typing a Chart ID into Production. Phase 10A-10B only establishes this flag and the import foundation; it does not change how the Production form itself behaves for either type - that is explicitly deferred (see "Future work" below).
- A Manager sets `allocationType` on project create or update (`POST`/`PATCH /manager/projects`); changing it is audit-logged (`PROJECT_UPDATED`, before/after) exactly like any other project field.

## Project ↔ Team Assignment History (Phase 10A)

- `Project.teamId` remains the single "current team" pointer every existing scope query (`chartScope`, `productionScope`, `auditScope`, `mine`, etc.) reads - **unchanged**.
- A parallel `ProjectTeamAssignment` table records every assign/unassign transition as an append-only history, mirroring the existing `VendorAssignment` pattern: reassigning closes the previous active row (`isActive: false`, `unassignedAt`/`unassignedById` set) and creates a new active row, in one transaction, rather than ever deleting a row.
- A database partial unique index enforces at most one `isActive: true` `ProjectTeamAssignment` per project at a time (Prisma's schema DSL cannot express a partial index directly, so - like `LoginNameAllocation`'s and `VendorAssignment`'s equivalent invariants - it is written as raw SQL in this model's migration).
- New endpoints: `POST /manager/projects/:id/team-assignment` (assign, body `{ teamId }`), `DELETE /manager/projects/:id/team-assignment` (unassign), `GET /manager/projects/:id/team-assignments` (full history). All Manager-only, all write an audit log (`PROJECT_TEAM_ASSIGNED`/`PROJECT_TEAM_UNASSIGNED`), all reuse the existing cross-vendor Auditor-fit check (`assertProjectAuditorsFit`).
- **Single source of truth (CORRECTED per architecture review):** the legacy `PATCH /manager/projects/:id { teamId }` path no longer has a second, silent behaviour. `ProjectsService.updateProject` now detects a `teamId` change and routes it through the exact same `closeAndOpenTeamAssignment` transaction that the two dedicated endpoints above use, so `ProjectTeamAssignment` history is written consistently regardless of which API a caller uses. There is exactly one way a Project's team relationship changes at the database level.
- **Project creation also creates history (CORRECTED, final round):** `POST /manager/projects` with a `teamId` supplied previously wrote `Project.teamId` directly, with no corresponding `ProjectTeamAssignment` row - leaving `Project.teamId` set but its history table empty. `ProjectsService.createProject` now creates the `Project` and (when `teamId` is supplied) its initial active `ProjectTeamAssignment` row **in the same database transaction**, so the two either both succeed or both fail - a Project is never left partially created with an inconsistent team-history state. When no `teamId` is supplied, no `ProjectTeamAssignment` row is created, exactly as before. This makes all three write paths (create, dedicated assign/unassign, legacy PATCH) consistent with one another.

## Client File Driven Chart Import (Phase 10B)

SmartCode's primary chart allocation mechanism is now **client-file-driven**, not manual per-chart assignment. This section covers only the import foundation; the Manager Allocation Summary export/workspace is explicitly **Phase 10C**, and the Team-Lead Summary-upload workflow that actually distributes imported charts to Coders is explicitly **Phase 10D** - neither is implemented yet (see "Future work" below).

**Raw vs. Summary.** The client's own workbook ("Allocation.xlsx") has exactly two sheets: **Raw** (the client's source data - what Phase 10B imports) and **Summary** (the Manager's future export/output format - Phase 10C, not implemented here). Import never falls back from Raw to Summary, or vice versa, even if the requested sheet is missing.

**Exact columns, never renamed.** The Raw sheet/CSV has exactly these six columns, matched by exact name (case-sensitive), never reordered-and-assumed, never renamed, and their values (`PageBucket`, `textbox9`, `EventTypeName2`, `High_Level_Status`) are stored and round-tripped verbatim - their meaning is never assumed or reinterpreted by the application:

    ChartID, PageCount, PageBucket, textbox9, EventTypeName2, High_Level_Status

The future Summary export's contract (Phase 10C, documented here only as a **future contract**, not implemented by this phase) adds exactly two more columns: `Assigned to` (blank until Phase 10D resolves it to a Coder's Login Name) and `Shift`. `Shift` does not appear anywhere in the Raw sheet supplied to this phase, so its source (client-provided vs. project-configured vs. generated) is **not yet defined** and is explicitly left to Phase 10C to determine - it must not be invented or erased by this phase, and this phase does not attempt to produce it.

**Import behaviour.**
- CSV or Excel (`.xlsx` only - legacy binary `.xls` is explicitly **not supported**, disclosed as a known limitation rather than silently mis-parsed; adding an `.xls` reader was judged an unnecessary new dependency for this phase).
- `POST /projects/:projectId/chart-imports/preview` validates and reports without writing anything (besides an audit log entry); `POST /projects/:projectId/chart-imports` re-validates server-side (the preview is advisory, the commit is authoritative - the same rule the existing Coder CSV importer already follows) and commits.
- Row-level validation: `ChartID` is required; `PageCount` is required and must be a whole number; the other four columns are passed through as-is with no validation, since their meaning is deliberately not interpreted.
- **Duplicate ChartID within the same file (CORRECTED per architecture review):** EVERY row sharing a ChartID that appears more than once in the file is flagged `duplicate` - not just the later occurrence(s) - and **none** of them are imported (e.g. "Row 18: Duplicate ChartID 609363220 found in row 7."). There is no business rule authorizing SmartCode to pick one occurrence as correct when duplicate rows disagree (e.g. different `PageCount`), so it picks none; the Manager must correct the file and re-upload.
- **ChartID that already exists under a different Project**: flagged `invalid` - re-importing a chart under a different project is rejected outright, since `Chart.chartId` is a single global identity that Production/Audit/Rework all key off.
- **ChartID that already exists under the SAME Project (CORRECTED per architecture review)**: left `valid`. At commit, this **never overwrites anything on the existing `Chart` row** - it only refreshes a lightweight `Chart.sourceImportId` "most recent import" pointer and appends a brand-new `ChartImportRow` (see "Provenance" below) - it never inserts a second `Chart` row, never touches that Chart's `ProductionEntry`/`AuditEntry`/`Rework` history, and never overwrites a prior import's values (every import's values are preserved, forever, as their own row).
- **Transaction safety**: a commit's `Chart`/`ChartImportRow` writes (in batches of 500 for large files) and its own `ChartImport` history row are written in one database transaction. If anything fails partway through, the whole transaction rolls back and a separate `ChartImport` row is written afterward with `status: FAILED` and zero successful rows - an import is never reported `COMPLETED` unless every row in that batch actually was. `PENDING`/`COMPLETED`/`FAILED`/`REJECTED` cover every state this phase can ever observe; `PROCESSING` was deliberately not added since a commit is always one synchronous transaction with no client-observable intermediate state (see `ChartImportStatus`'s doc comment in `schema.prisma`).
- **All-or-nothing import (CORRECTED, final round):** if **any** row in the file is `invalid` or `duplicate` - not only when there are zero valid rows - the **entire file is rejected** (`status: REJECTED`, HTTP 400) before any `Chart` or `ChartImportRow` is ever touched, and before any existing `Chart.sourceImportId` is refreshed. A file that is 998/1000 valid is not "998 imported, 2 rejected" - there is no business rule authorizing SmartCode to import part of a client's chart inventory file while silently discarding the rest, so the write transaction below is only ever entered once every single row has validated successfully. The Manager must correct every flagged row and re-upload the whole file.
- **MANUAL-only workflow (CORRECTED, final round):** `preview()` and `commit()` both verify `project.allocationType === 'MANUAL'` server-side before doing anything else; an `AUTOMATIC` project's request is rejected with `"Client chart import is available only for MANUAL allocation projects."` (HTTP 400), never relying on the frontend to withhold the option. This mirrors the "Project Allocation Type" rule above: an `AUTOMATIC` project has no client allocation file at all - the Manager selects a Team and the Coder enters `ChartID`/`PageCount` directly in the Production Workspace - so this workflow must never be reachable for one. `listHistory`/`getHistoryDetail` (viewing past import history) are **not** restricted by allocation type, since they are read-only and not scoped to how a chart's data arrived.
- Manager-only (`RolesGuard` + `@Roles('MANAGER')`) - Vendor, Team Lead, and Coder have no import permission. Every step is audited (`CLIENT_CHART_IMPORT_PREVIEW`/`_STARTED`/`_COMPLETED`/`_FAILED`/`_REJECTED`).

**Import History.** `ChartImport` is a persisted, queryable row per commit attempt (not written for a preview) recording: project, who imported it and when, original filename, file type, row counts (total/valid/invalid/duplicate/success/failed), status, the template version used, and a capped (200-message) list of row-level validation messages - never the raw file contents, and never a full per-row dump. `GET /projects/:projectId/chart-imports` lists this history (paginated, most recent first); `GET .../chart-imports/:id` returns one record's full message list.

**Provenance (CORRECTED per architecture review): `ChartImportTemplate` → `ChartImportTemplateVersion` → `ChartImport` → `ChartImportRow` → `Chart`.** An earlier draft of this phase stored the client's attribute values (`PageCount`/`PageBucket`/`textbox9`/`EventTypeName2`/`High_Level_Status`) directly on `Chart`, and collapsed "Template" and "TemplateVersion" into one table keyed directly off `Project`. Both were corrected:
- **`ChartImportTemplate`** is now its own row - one per Project, created lazily on that Project's first import - representing the project-level template identity.
- **`ChartImportTemplateVersion`** belongs to `ChartImportTemplate` (not directly to Project); a new version is only created when a Project's imported header set differs from its current active version.
- **`ChartImportRow`** is new: the actual source-of-truth for a client-imported chart's attribute values, one row per `(import, chart)` pair, **insert-only, never updated or overwritten**. Re-importing an already-imported ChartID always appends a brand-new `ChartImportRow` rather than mutating anything, so every historical set of client-provided values for a ChartID survives forever, even across repeated imports with changed values.
- **`Chart`** itself gained only one new nullable column, `sourceImportId` - a cheap "most recently touched by this import" convenience pointer, refreshed on every (re-)import. It is never the source of truth for historical attribute values (`ChartImportRow` is), and refreshing it never writes to `ProductionEntry`/`AuditEntry`/`Rework`.
- For any ChartID, "where did this come from" is always answerable precisely: `ChartImportRow` → its `ChartImport` (project/file/importedBy/importedAt) → its `ChartImportTemplateVersion` (project/version/headers). A dedicated "chart provenance" endpoint was judged unnecessary this phase (the existing import-history endpoints already expose every piece of this chain); it can be added later without a schema change if a direct "show me this chart's import history" screen is ever needed.

**No Manager Allocation Summary export in this phase (CORRECTED per architecture review).** An earlier draft of this phase implemented `GET /projects/:projectId/chart-imports/summary-export`. That has been **removed** - the Manager Allocation Workspace (filters, dashboard, "Export Current Filter", Summary export) is Phase 10C's scope, not 10A-10B's backend-foundation scope, and building it now would be building ahead of the agreed phase structure. Nothing about `ChartImportRow`/`ChartImportTemplate` needed to be removed to make this cut - the provenance foundation stands on its own regardless of when the export UI is built.

**No manual per-chart allocation UI.** This phase does not add, and explicitly must not add, a screen where a Manager picks "Chart A → Coder X" one at a time - the only supported allocation mechanism is the client-file import above.

**Future work (explicitly NOT implemented by Phase 10A-10B - do not confuse with what's documented above):** the Manager Allocation Workspace and Summary export (**Phase 10C**); the Team-Lead Summary-upload workflow; resolving an uploaded "Assigned to" Login Name against `LoginNameAllocation`, including its active/role/scope checks; automatic population of a Coder's Production Space from an allocation; pullback/reassignment; a realtime allocation dashboard; a Coder EOD export; the Manual/Automatic Production Workspace UI changes an `allocationType` value will eventually drive; NAS/local-agent integration; a registration station (**Phase 10D or later**).
- Enforced server-side for Manager only (route-level `@Roles('MANAGER')` guard on both `manager/login-name-allocations` and `manager/employees`) — hiding the nav entry for other roles is a convenience, not the security boundary.

## Chart Allocation (Phase 10D)

Delivers the workflow the two sections above deferred: the Manager Summary export, the Team Lead's Login-Name upload, and pullback/reassignment. This section supersedes the "Future work" list above for the items it covers; the client Raw-file import (`ChartImport`/`ChartImportRow`/`ChartImportTemplate`, Phase 10B) is unchanged and untouched by this phase, and `apps/web/src/features/charts/ChartRepository.tsx` is unchanged - Chart Allocation is a separate workspace/tab, not a replacement.

**Model.** `ChartAllocation` is the append-only allocation ledger (mirrors the `VendorAssignment`/`LoginNameAllocation`/`ProjectTeamAssignment` pattern already in this schema): one row per allocation event, `isActive: true` for the current one, `isActive: false` with `endedAt`/`endedById`/`endReason` (`PULLED_BACK` or `REASSIGNED`)/`endNote` for a closed one, and `previousAllocationId` linking a reassignment to what it replaced. A database **partial unique index** (`WHERE "isActive" = true`, raw SQL - Prisma's schema DSL cannot express this, same technique as the three sibling tables above) guarantees at most one active allocation per `chartId` at the database level, independent of any application-level check. `Chart.assignedCoderId`/`assignedById`/`assignedAt` (added in Phase 10A-10B as unconstrained, unused scalars reserved for this phase) are now wired to real foreign keys and serve as a cheap "current assignment" pointer for scope/list queries; `ChartAllocation` is always the source of history, never that pointer. `ChartAllocationImport` records each Team Lead Summary-upload attempt, mirroring `ChartImport`'s shape and reusing its `ChartImportFileType`/`ChartImportStatus` enums rather than duplicating them.

**Manager: Summary export.** `GET /projects/:projectId/chart-allocations` (list/filter) and `GET .../chart-allocations/export` (Manager-only, MANUAL projects only) produce the client's exact Raw columns (from the latest `ChartImportRow` per Chart - Raw data itself is never modified) plus a column always blank ("Assigned to") and a column always fixed to the literal value `Shift 1`. The Manager has **no per-chart manual-assign form** - the only way a `ChartAllocation` is created is the Team Lead's Summary upload below.

**Team Lead: Summary upload (`preview`/`commit`, all-or-nothing).** `POST .../chart-allocations/preview` validates without writing; `POST .../chart-allocations` re-validates authoritatively and commits, in one transaction, exactly mirroring `ChartImportsService`'s preview/commit shape. Per row: `ChartID` must be present and belong to this Project; the Login Name must exist, belong to an **active `CODER`** account, and that Coder must be on this Project's Team; a duplicate `ChartID` within the same file flags **every** occurrence (none imported), identical to the Raw importer's own rule; a `ChartID` already actively allocated to a **different** Coder is rejected (use Reassign instead) and rejects the whole file. **Any** invalid or duplicate row rejects the **entire** upload (`status: REJECTED`) - nothing partial is ever written. A successful commit creates one `ChartAllocation` per newly-allocated row and refreshes `Chart`'s current-assignment pointer, all in one transaction; a concurrent duplicate-allocation race is caught by the partial unique index and surfaced as `409 Conflict` (`CHART_ALLOCATION_FAILED` audit + a `FAILED` import row), never a false success.

**Two documented interpretations (the given rules did not fully resolve these; disclosed here rather than invented silently):**
- **Blank "Assigned to" rows are not allocation instructions.** The Manager's export leaves every row blank; a Team Lead need not fill in every row of one export in one upload. A row whose "Assigned to" is still blank on re-upload is silently excluded from `totalRows`/`validRows`/`invalidRows`/`duplicateRows` and from what gets written - it is not rejected as "incomplete." A commit whose every row is blank is rejected outright ("nothing to allocate").
- **Re-uploading an unchanged assignment is a no-op, not a duplicate.** "A Chart already actively allocated → reject the row" and "never create a second allocation when the same chart is uploaded again" both hold: a row allocating a chart that is **already actively allocated to a different Coder** is rejected (use Reassign); a row allocating a chart **already actively allocated to that same Coder** is treated as a harmless idempotent no-op - reported as a successful row, but no new `ChartAllocation` is written and `Chart`'s pointer is not touched again.

**Pullback.** `POST .../chart-allocations/:chartId/pullback` (Manager, or the Team Lead of that Project's Team) ends the active allocation (`isActive: false`, preserved forever) and clears `Chart`'s current-assignment pointer - it never deletes a `ChartAllocation` row. Blocked when the chart's current production is `COMPLETED` (explicit instruction: "do not pull back completed production") or when the chart has a live `Rework` (`OPEN`/`IN_PROGRESS`/`RESOLVED` - reused directly from `rework.workflow.ts`'s own `LIVE_REWORK` set, not invented). **Disclosed gap:** pulling back a chart whose production is merely `PENDING`/`IN_PROGRESS`/`REWORK` (not yet `COMPLETED`, and with no live rework) is **not** blocked - the given rules only forbid pulling back completed work, and no existing `ProductionEntry` state rule forbids this case, so nothing further was invented. If a stricter rule is wanted here (e.g. also blocking on `IN_PROGRESS`), it should be added as its own explicit decision.

**Reassignment.** `POST .../chart-allocations/:chartId/reassign` validates the new Coder (exists, active, `CODER` role, on this Project's Team, not already the current holder) **before** changing anything, then atomically ends the current allocation (`endReason: REASSIGNED`) and creates a new one linked via `previousAllocationId`, in one transaction - both operations succeed or both roll back together.

**History and metrics.** `GET .../chart-allocations/history` (the `ChartAllocation` ledger, most recent first) and `GET .../chart-allocations/import-history` (Team Lead upload history) are available to the Manager and to the Team Lead of that Project's Team. `GET .../chart-allocations/metrics` returns **raw counts only** (allocated/done/pending, overall and per-Coder, derived from actual `ChartAllocation`/`ProductionEntry` state) - no production-percentage or CPH-style formula is invented here, per explicit instruction.

**Coder Production scoping (MANUAL projects only; AUTOMATIC projects are entirely unaffected).** `chartScope`'s `CODER` case (`common/scope.ts`) now also matches charts with an active `ChartAllocation` for that Coder, so an allocated-but-not-yet-coded MANUAL chart appears in the Coder's Chart Repository. `ProductionService.create()` gained two additive checks, both gated on `project.allocationType === 'MANUAL'` so `AUTOMATIC`-project behaviour (and its existing tests) is completely unchanged: (1) submitting production for an *existing* MANUAL-project chart requires an active `ChartAllocation` for the calling Coder, or it is rejected (`ForbiddenException`); (2) a Coder may not self-create a *brand-new* chart in a MANUAL project - MANUAL charts only come from the Raw import + Team Lead allocation workflow above. Chart ID and imported `PageCount` remain read-only source values for the Coder; ICD/DOS/Remarks remain editable exactly per the existing production rules. No CPH/Production%/Quality% formula was introduced or changed.

**Frontend.** A new, separate `features/chart-allocation/` module (`ChartAllocationWorkspace` for the Manager, `TeamLeadAllocationUpload` for the Team Lead) is rendered as an additional **tab** on the existing Manager and Team Lead Charts pages, alongside the unmodified "Chart Repository" tab (`ChartRepository.tsx` itself has no changes). The Manager tab lists/filters a MANUAL project's charts, exports the Summary, shows allocation metrics, and can pull back or reassign; the Team Lead tab uploads a Summary file, shows the row-level preview before committing, and lists recent uploads.

**Testing note.** `chart-allocations.service.spec.ts` (22-item test list) and additive `production.service.spec.ts` cases for the two new MANUAL-project checks were written against the same Jest/`Test.createTestingModule` mocking pattern as the existing `chart-imports.service.spec.ts`. In this sandbox, `prisma generate` cannot run (`binaries.prisma.sh` is not on the outbound allowlist, confirmed via the proxy status endpoint - a pre-existing, environment-wide limitation, not introduced by this phase), so the generated `@prisma/client` has no model types. This blocks TypeScript compilation - and therefore `ts-jest` test execution - for **every** service module in `apps/api`, including the pre-existing `chart-imports.service.spec.ts` and `production.service.spec.ts` (verified: they fail to compile in this same sandbox for the identical reason, unrelated to any change in this phase). The new and modified test files here are unaffected by this in kind - they are ready to run wherever the Prisma client is properly generated - and were reviewed line-by-line against the service's actual logic rather than only written and left unverified.

## Organization Assignment + Auto-Visibility

Delivers the "FINAL ORGANIZATION ASSIGNMENT + AUTO-VISIBILITY REQUIREMENT" document: a Team Lead's "Relieve from Team" action, and a single backend-derived "what is my current organizational context" surface every role's dashboard consumes instead of asking the user to re-select an already-assigned Team/Project.

**Schema (minimum necessary, per the requirement's own instruction).** Two additive, forward-only changes, both following patterns already established elsewhere in this schema:
- **`TeamMembership`** - a new append-only ledger for Coder↔Team history (mirrors `ProjectTeamAssignment`/`ChartAllocation`: `isActive`, `assignedAt`/`assignedById`, `endedAt`/`endedById`/`endReason` (`RELIEVED` or `REASSIGNED`), with a partial unique index enforcing at most one active membership per Coder). `User.teamId` is **unchanged** and remains the single current-state pointer every scope/RBAC helper reads - this table only adds parallel, queryable history. A shared helper (`common/team-membership.ts`: `setCoderTeam`/`cascadeCodersToTeam`/`cascadeCodersOffTeam`/`openMembership`) is the only code path allowed to change a Coder's `teamId`, so the pointer and the ledger can never drift apart. Pre-existing Coder↔Team relationships are **not backfilled** into the ledger (same reasoning as `LoginNameAllocation`'s own un-backfilled initial rows: IDs are Prisma-client-generated, not DB-generated, so a raw-SQL backfill INSERT has no safe way to mint them) - the ledger starts recording from the next assignment change onward; `User.teamId` itself is untouched and every existing query keeps working.
- **`AuditorProjectAssignment`** gains `isActive`/`removedAt`/`removedById` (soft-delete columns, mirroring `VendorAssignment`). Unassigning an Auditor from a Project (`ProjectsService#deleteAssignment`, "Reassign Auditor") used to hard-`DELETE` the row, losing history; it now soft-deletes, so "historical assignments remain intact" holds for Auditors too. The old `@@unique([auditorId, projectId])` (which only worked because a delete freed the pair) is replaced by a partial unique index scoped to `isActive = true`. **Every** query that used to derive Auditor→Project scope or counts from this table (`chartScope`'s cousin `auditorProjectWhere`, `assertProjectAuditorsFit`, `assertAuditorFitsProject`'s caller in `VendorsService#assign`, `AuditsService#chartForCaller`, the Manager's vendor/project auditor counts, the Auditor's own dashboard) was audited and updated to filter `isActive: true` - a soft-deleted assignment must never keep granting access, matching "RBAC prevents unauthorized cross-Vendor/cross-Team access" for the Auditor role too.

**1. Team Lead: "Relieve from Team".** `POST /team-leads/coders/:id/relieve` (`CodersService#relieveFromTeam`, Team-Lead-only, scoped to their own team via the existing `findOwn`/`this.scope` lookup - the same 404-for-outside-scope behaviour as every other Coder route). Ends the Coder's active `TeamMembership` row and clears `User.teamId` in one transaction; never touches `isActive`, `vendorId`, or any `ProductionEntry`/`AuditEntry`/`Rework`/`ChartAllocation` row. Enforced **server-side** (not frontend-only, per the requirement's explicit instruction) - the frontend's `ConfirmDialog` is a UX courtesy, never the actual authority. The Coder immediately stops matching `teamId`-scoped queries (active-team-member lists, new Team-scoped work) while every historical record stays intact and queryable.

**2/9/12. Automatic assignment visibility - single source of truth.** `GET /me/context` (`OrgContextModule`/`OrgContextService`) is a single, role-aware endpoint every dashboard calls on load - CODER/TEAM_LEAD/AUDITOR/VENDOR each get their current Vendor/Team/Team Lead/Project(s) (MANAGER gets `{ scope: 'ENTERPRISE' }`, since it has none of these). It is built entirely from primitives that already existed for this exact purpose - `common/org-ref.ts`'s `orgVendorRef`/`orgTeamRef`/`orgTeamLeadRef` (already used by Employee Directory and Login Name Allocation) and the same authorized-projects `where` logic `ProjectsService#mine` already used - rather than a new parallel resolution path or duplicated assignment data (requirement section 9's explicit instruction). The "project switcher, authorized projects only" requirement (section 12) needed **no new code**: `ProductionForm`/`AuditQueue`/the Chart Allocation workspaces already build their project pickers from `useMyProjects()` (`GET /projects/mine`), which was already authorized-only and already the single source of truth - confirmed by re-reading those call sites rather than assumed.

**3/4/5/6/7. Per-role dashboards.** A new `OrgContextBanner` component (`apps/web/src/components/data/OrgContextBanner.tsx`), fetching `GET /me/context` via a small React Query hook, is rendered on the Coder/Team Lead/Auditor/Vendor dashboards (not the Manager's - enterprise scope has nothing to show here) showing exactly the fields the requirement names per role (Coder: Assigned Project/Team/Team Lead/Vendor; Team Lead: Team/Project(s)/Vendor/Coder count; Auditor: Project(s)/Client(s)/Vendor; Vendor: Teams/Team Leads/Projects/Coder count/active users) - all backend-derived, none hardcoded or manually entered.

**8. Manager Employee Directory.** `EmployeeRow`/`EmployeeDetail` gain `assignedProjects: {id,name}[] | null` (`null` for MANAGER - enterprise scope is not a per-project assignment, not an empty list). For CODER/TEAM_LEAD this is the same Team→Project relation `org-ref.ts` already resolves (`orgProjectsRef`, new); for AUDITOR it is their active `AuditorProjectAssignment` rows; for VENDOR (not reachable from a single `User` row - a Vendor's projects span every Team under it) `EmployeesService` batch-resolves it per distinct `vendorId` on the page via the existing `vendorProjectWhere` builder. No new table, no duplicated assignment data - exactly the "single source of truth" instruction in section 9.

**10. Assignment changes reflect automatically.** Every mutation that changes a Coder's Team (`relieveFromTeam`, the Vendor→Team-Lead cascade in `VendorsService#assignTeamLead`/`removeTeamLead`) already invalidates the existing `['coders']`/`['dashboard']` React Query keys on the frontend; that invalidation now also covers `['org-context']` and `['employees']`, so a relieved/reassigned Coder's own next dashboard load, and the Manager's Employee Directory, pick up the change with no manual refresh and no server-side polling.

**11. Explicit relieve/reassign actions - what already existed vs. what this phase added.** "Team Lead: Relieve Coder from Team" is new (above). "Manager: Unassign Team from Project" (`ProjectsService#unassignTeam`, via `ProjectTeamAssignment`), "Manager: Reassign Team Lead" (`VendorsService#assignTeamLead`, which already cascades every affected Coder's team), and "Manager: Reassign Auditor" (`ProjectsService#deleteAssignment` + `createAssignment`, now soft-delete) already existed and needed no new endpoint - only the Auditor path's history gap (above) and this phase's frontend query-invalidation update. **Disclosed interpretation gap:** "Manager: Reassign Coder/Team as permitted" has no dedicated new Manager→Coder team-reassignment endpoint here - the Manager hierarchy in this codebase has never let a Manager directly manage a Coder (Coders are created/managed by their Team Lead or Vendor; `canCreateRole` never permits `MANAGER → CODER`), and the Vendor→Team-Lead cascade is the existing mechanism by which a Manager's action moves a whole vendor's Coders between Teams. Inventing a new direct Manager-to-Coder assignment surface would go beyond "the minimum necessary" and touch the existing hierarchy rule the standing constraints say not to change unnecessarily; if a direct Manager override is actually wanted, it should be scoped and confirmed as its own decision.

**13. Schema/API sufficiency.** `User → Vendor → Team → Team Lead → Project` and `Auditor → Project` are both now representable with historical tracking: the Coder↔Team leg via the new `TeamMembership` ledger (the only leg that had none before), every other leg (`VendorAssignment`, `Team.teamLeadId`, `ProjectTeamAssignment`, and now `AuditorProjectAssignment`) already had or now has real history. No data is duplicated purely for display - `GET /me/context` and the Employee Directory's `assignedProjects` both compute from these same relations at read time.

Testing.** `coders.service.spec.ts` gained a `relieveFromTeam` suite (ends the ledger row + clears `teamId`, rejects a Vendor/Manager caller, rejects a cross-team Coder with the standard 404, rejects a Coder not currently on a team). `projects.service.spec.ts` gained a `deleteAssignment`/`listAssignments` suite (soft-delete shape, rejecting a double-removal, `includeEnded` defaulting to active-only). `audits.service.spec.ts`'s mock was updated for the `findUnique(auditorId_projectId)` → `findFirst({isActive: true})` change the soft-delete required. A new `org-context.service.spec.ts` pins the per-role `GET /me/context` shape, including "no team → empty projects, never a fake/default project."
